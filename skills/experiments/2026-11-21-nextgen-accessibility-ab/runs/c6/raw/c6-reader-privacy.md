### F1. Clicking "Audio briefing" sends a separate, loggable request that shows the reader chose audio
- Where: `bulletin.html`, the script at the end of the body (`new Audio('audio-briefing.mp3').play()` in the `#audio` click handler) and the button `Audio briefing (1 minute)`.
- Problem: The MP3 is fetched only when the reader clicks. The server therefore receives a request for `audio-briefing.mp3` that it would not otherwise get. That request carries the reader's IP address, user agent, any cookies set for the origin, and a `Referer` naming the bulletin page. Choosing audio is a choice of form, not a declaration of disability. Even so, a log of who chose audio is a weak signal that can suggest a visual, reading or cognitive need, and it can be joined to other requests from the same client. The page sends no analytics or beacon events, so the signal exists only in ordinary server or CDN access logs. What the office keeps in those logs, for how long, and whether it joins them to cookies is not shown.
- Who is affected: Readers who choose the audio briefing, a group that may include blind, partially sighted, dyslexic and cognitively disabled readers, among others.
- Impact: Low on the evidence given. The request is an ordinary static-asset GET with no need-revealing parameter. The risk depends on log retention and on joining the logs to identifiers, neither of which is visible here. If logs are kept per IP or per cookie and analysed for "audio users", the result could count as inferred special category data (UK GDPR Art. 9; ASSUMED, not advice).
- Severity: 1
- Fix: Keep the fetch as an ordinary, parameter-free static GET (as it is now). Serve media from the same origin without cookies, or from a cookieless static host. Do not log per-client identifiers for media assets, or truncate them. Do not add play or click analytics to this button. Another option is a native `<audio controls preload="metadata" src="audio-briefing.mp3">`, which can be shown to every reader so that playback is not a separate tracked step. If page-level analytics are ever added, state in the privacy notice that audio and transcript choices are not recorded.
- Evidence: `bulletin.html` lines `<p><button type="button" id="audio">Audio briefing (1 minute)</button> ...` and `document.getElementById('audio').addEventListener('click', () => new Audio('audio-briefing.mp3').play());`. No analytics script, beacon, cookie-setting code or third-party resource appears in the file.
- Needs disabled readers: no

### F2. Fetches of the audio and the script together can form a small format-preference profile (composition leak)
- Where: `bulletin.html`, the `Audio briefing script` link (`audio-briefing.txt`) next to the audio button.
- Problem: Each resource is harmless alone. The pattern of requests can still separate readers: for example, script fetched without audio, audio without script, or both. Joined with the user agent, IP address and request timing in the same log, this pattern adds bits to a client profile. It can be read as hinting at a hearing-related or vision-related preference. Today this adds little, because there are only two optional resources and no settings, toggles or simplify or Easy Read paths on the page. The risk grows if more per-format resources are added and fetched one by one (Easy Read, large print, plain language).
- Who is affected: Readers who use the script instead of the audio, or the reverse, which may include Deaf and hard-of-hearing readers and screen-reader users.
- Impact: Low now. It becomes higher if the office adds more on-demand adapted versions as separate URLs and keeps per-client logs. It is not need-revealing on its own (ASSUMED: inference from request patterns could still be personal data under UK GDPR, not advice).
- Severity: 0
- Fix: Keep adapted versions as plain static URLs with no query parameters, profile or account lookup, and no "accessible version" cookie. Apply the same log minimisation as F1 to every alternative-format asset. When more versions are added, consider putting the transcript inline in a `<details>` element on the page, or bundling versions, so that choosing one does not cause a distinct request.
- Evidence: `<a href="audio-briefing.txt">Audio briefing script</a>` is a separate resource from `audio-briefing.mp3`. No preference storage of any kind (localStorage, cookie, URL parameter) appears in the file.
- Needs disabled readers: no

Not found: I looked for the following on this page and did not find them. Any URL parameter, header, cookie, localStorage or account setting that carries a reader preference. Analytics, beacon or third-party scripts, fonts or embeds. Detection of assistive technology (no screen-reader or `prefers-*` sniffing reported back, no ARIA-probe scripts). Settings panels or toggles for high contrast, reduced motion, fonts, simplify or Easy Read. Any form or request route for alternative formats that asks the reader to disclose a disability or state a purpose. Anything that blocks on-device adaptation (the viewport allows zoom; sizes are in rem). The `/accessibility` page and any alternative-format request process behind it are not in the case material, so their disclosure requirements could not be checked. Server and CDN log retention and the privacy notice are also not supplied.
